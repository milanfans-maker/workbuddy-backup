# 软件著作权登记材料生成

为一款软件产出可直接上传到 CPCC 登记系统的整套材料。核心是把「代码 → 合规 PDF」这条最容易翻车的排版链做对。

## 0. 先问清 5 个字段（猜不得）

著作权人姓名（必须与身份证/营业执照一致，笔名无效）、软件全称与版本号、
开发完成日期、发表状态（已发表 → 还要首次发表日期 + 发表地点 + 发表证明；未发表最省事）、
个人信息（身份证号/地址/电话/邮箱）。**软件名称含他人商标（如 QQ）建议去掉**，否则可能被要求改名。

## 1. 硬性格式要求（CPCC）

| 材料 | 要求 |
|---|---|
| 源程序 | 前 30 页 + 后 30 页（不足 60 页全交）；**每页不少于 50 行**（末页除外）；页眉标注软件名称 + 版本号 + 页码，页眉与正文用横线隔开；从代码第一行起排，**不要加封面** |
| 说明书 | 需含**运行环境、功能说明、操作步骤**，配界面截图；页眉同样标注软件名称 + 版本号；超过 60 页交前后各 30 页，不超则全本提交 |
| 名称/版本一致 | 申请表 = 源程序页眉 = 说明书页眉，**三处必须逐字相同** |
| 官费 | 2017-04-01 起已取消，免费 |

### ⚠️ 日期逻辑（官方填表说明，最容易踩）

> 首次发表日期「**须在开发完成日同日或者之后**」。

也就是说 **开发完成日期 ≤ 首次发表日期**，反过来一定会被要求补正。
用户很容易给出「今天才完成开发 / 但上个月就发表了」这种自相矛盾的两个日期 ——
**每次都要主动算一遍**，发现冲突就把开发完成日期前移到发表日期之前（如「9-1 完成 → 9-2 发表」），
并在交付说明里写清为什么改。
（另有「开发完成日期应比申请日提前 2 个月」的说法，那是代理机构的经验之谈，**官方无此要求**，不必强求。）

## 2. 三步流程

1. **源程序 PDF**：A4 纵向；正文宽 = 595.28 − 左右边距 → 用内置 `Courier`（0.6em 等宽）排 ASCII、
   `Arial Unicode MS` 排中文；**逐字符按 `pdfmetrics.stringWidth` 累加宽度折行**（源码常含 10 万字符级
   base64 内嵌资源行）；页眉左=软件名+版本、右=页码。
2. **说明书 PDF**：reportlab **Platypus**；H1/H2/H3 + 正文（首行缩进 2 字符）+ 表格 + 图片 + 图注；
   封面用 `NextPageTemplate('body')` 切模板使封面无页眉页脚。
3. **配图**：headless Chrome 实拍各功能界面（视口截图 + 元素截图），再嵌进说明书。

## 3. 十个必须知道的坑

1. ⚠️ **reportlab 加载不了 CFF（PostScript 轮廓）字体**。`Hiragino Sans GB.ttc` 会抛
   `TTFError: postscript outlines are not supported`。macOS 上能用的是
   `/System/Library/Fonts/Supplemental/Arial Unicode.ttf`（字形最全）与 `STHeiti Light/Medium.ttc`。
   **先扫描字体再动手**：`TTFontFile(path, subfontIndex=i).charToGlyph` 拿字形表，
   查目标字符（如 `软`）是否命中。
2. ⚠️ **每页行位要按「可见行」倒推，不能直接按 50 排**。源码空行也占行位，
   50 行位时实测可见行最少只有 45 ⇒ 会被判不足 50 行。**实测做法：排 60 行位**，
   校验脚本用 pymupdf 数「基线 y ≥ 页眉线以下」的文本行，逐页确认 ≥ 50。
3. ⚠️ **源文件尾部纯空行会让末页整页留白**（pymupdf 数出 0 行）。算页数前先把
   `disp` 末尾的空白显示行 pop 掉。
4. ⚠️ **页码计数器要在 `on_page` 里无条件自增**。写成 `if n > 0: draw(第 n 页)` 会让第一个正文页没有页码。
5. ⚠️ **字体缺字只影响渲染，不要改源文件**。Arial Unicode 缺 emoji 与 `⚠`(U+26A0)；
   遇到无覆盖字符就换字体、仍无则用 `□` 呈现，并统计次数供说明。变体选择符（U+FE0F）宽度记 0、不绘制。
6. ⚠️ **超长竖图（手机整页截图）嵌不进 PDF**：1122×12621 缩到限高后只剩 43pt 宽、完全不可读。
   改拍单屏图；配图统一先缩到 1500px 宽转 JPEG(q90)，体积能降一半以上。
7. ⚠️ **说明书中出现网址/联系方式是补正高频项**。用户给的发表链接、官网、邮箱、手机号
   **一律只写进 `04`/`05` 两个 md**，绝不进说明书 PDF。终检脚本要用正则拦：
   `https?://|www\.`、`[\w.+-]+@[\w-]+\.[\w.]+`、`(?<!\d)1[3-9]\d{9}(?!\d)`。
8. ⚠️ **截图脚本自己会「重号」**：若某一步的编号是直接读计数器（`String(shot)`）而**忘了 `shot += 1`**，
   该图会与上一张同名覆盖，后续文件名整体前移一位。写完截图脚本先核对「张数 = 文件名序号最大值」，
   再核对说明书里引用的每个 `man_NN_*` 都真实存在。
9. ⚠️ **截图前要等状态提示浮层（toast）自动消失**，否则「分析完成：共 N 步…」会压在棋盘正上方入镜。
   做法：轮询该元素 `getComputedStyle(...).display !== 'none'`，最多等 6s。
10. ⚠️ **源码里内嵌的 base64 资源要量化并写进备查说明**。一个 12 万字符的 base64 行折行后占
    1,200+ 显示行，可能吃掉前 30 页里的十几页。**不要删改源码**，而是在 `05` 里写明
    「第 X–Y 页为内嵌图像资源编码数据，占前 30 页的 Z%，未作任何删改」，并给审查员一句标准答复。

## 3b. 多版本软件：先定「登记哪一版」

同一软件常有多个并行版本（如「玩家版 / 竞技版」，区别就是某个功能模块）。
登记前必须确认**登记哪一版**，并且：

- **源程序与说明书配图必须取自同一版本** —— 否则说明书截图里会出现登记版本根本没有的模块
  （实测踩过：源程序取玩家版、截图取另一版，图上多出一整块计分卡片）。
- 未纳入登记的那一版**原样保留即可**，不必为了「材料里没有它」去改产品；
  两个版本可以日后再分别登记，互不冲突。
- 建议在 `04` 里写一节「本次登记的版本范围」：登记源文件、等价文件（哈希）、未纳入登记的文件及原因。

## 3c. 说明书配图必须筛样本（有真实外泄风险）

界面截图会**连带显示软件正在处理的数据** —— 文件名、玩家名、账号名等。若这些内容里
出现第三方姓名或敏感字样，会原样印进登记材料。**不要随手拿一份数据就拍**：

1. 先确认界面会把哪些字段显示出来（如「来源文件」「玩家列表」），再决定要筛什么；
2. 写一个扫描脚本，批量过一遍候选数据，按黑名单（第三方姓名 + 敏感/不雅词）**剔除**并打印剔除原因；
3. 从剩下的里挑内容最丰富的（步数多、事件类型全）作为示例；
4. 扫描结果与选定样本写进 `05` 备查（证明「不是没想过」）。

### 3d. 正向条件：示例数据里的「本人身份」字段

黑名单只是**剔除**，还要一条**正向要求**：示例数据应当能体现著作权人本人 ——
例如对局复盘类软件的示例棋谱，其「己方 / 录制者」必须是著作权人的网名，
这样与 `04` 里登记的网名（含网名归属表）互相印证；若示例里显示的本人身份是第三方，材料会自相矛盾。

- ⚠️ **该字段往往不在界面上显式出现**，而藏在数据文件内部（本项目实测：`.jgs` 文件头的 `0x0F`
  颜色字节指示录制者/己方颜色）。**用程序自身的判定函数读**（`ownColorOf(replay)`），
  **不要靠二进制搜名字** —— 名字出现在文件里 ≠ 它是己方（本项目 189/191 份棋谱都含同一网名，
  因为都是本人参与的对局，但「己方」只有一位）。Python 可直接 `bytes.decode('gbk', errors='ignore')`
  搜出 `.jgs` 内的中文网名（Node 侧无 GBK 解码），适合做**粗筛**；精确判定仍走程序逻辑。
- ⚠️ **软件内置的 demo 数据是「第二份示例数据」**。界面上那个「载入示例 X」按钮对应的数据通常以
  base64 内嵌在源码里，与截图时用的示例数据**未必是同一份**，两份都要核。
  若说明书正文写了「点击『载入示例 X』…」，读者会默认后面的截图就是那份 ——
  要么让两者一致，要么在正文里避免这种暗示。
- ⚠️ **替换内嵌 demo 数据 = 改源码**。内嵌 base64 的字节数一变，折行页数随之变化，
  前/后 30 页的页码分配全部位移 ⇒ 必须重出源程序 PDF。**示例数据要在冻结源程序 PDF 之前定死。**
- ⚠️ **先确认用户看的是哪一版，再决定动不动文件**。本次实测：用户要求「示例棋谱换成己方是本人的」，
  而**当前版早已满足**，问题出在他手上是上一版备份 —— 旧版示例的己方是另一个人（「开除」）。
  核对方法：比对两版截图的样本特征（玩家名 / 来源文件名），把新旧两版的差异摆出来再确认意图。
- 加一条**逐图核验脚本**：重放截图脚本的每一个界面状态，抓取「带『己方』标签的卡片」「棋盘名字标签」
  「统计区」「评估区」「手机端」「全屏窗」的文本，断言本人网名处处出现、且四家网名无敏感词；
  顺带把「己方此局是胜是败」也读出来 —— 示例里本人落败没有合规问题，但值得主动告知用户
  （库里通常有大量「己方取胜」的等价候选可换）。

### 3e. 上传环节：源程序必须合并成「单个 PDF」，文档不足 60 页照交

CPCC 在线系统「材料上传」页共**三栏**（实测 `register.ccopyright.com.cn/r11.html#features`）：

| 栏目 | 必填 | 交什么 |
|---|---|---|
| **程序鉴别材料** | 必填 | 提示语「源程序前连续的 30 页和后连续的 30 页」，**只有一个上传框** ⇒ 前 30 + 后 30 **合并为一个 PDF**（60 页；页码 1–30 接 100–129，中间跳号正常） |
| **文档鉴别材料** | 必填 | 说明书（或任一文档）前/后各连续 30 页；**不足 60 页的全部提交** |
| **其他相关证明文件** | 非必填 | 首次发表证明 / 身份证明等，可留空 |

- ⚠️ **交付前必须把前/后 30 页合并好**，别让用户拿 `01`、`02` 去分两次传 —— 那栏根本没法传两个。
- ⚠️ **只做了 24 页的说明书不是缺陷**：规程即「不足 60 页的全部提交」。
  顺手在 `05` 里备一句答复：**「文档全部内容为 N 页，已按规程全部提交。」**
- 交存方式选 **一般交存**（例外交存是申请保密/遮盖的特殊程序，别选错）。
- 归置方式：在材料目录下开 `上传用/`，放「已合并、可直接上传」的两份 PDF，
  并在 `05` 里做成「系统栏目 → 上传哪个文件 → 页数/大小」对照表，用户照着点即可。

合并 + 自核（pymupdf）：

```python
import pymupdf                      # 合并
d = pymupdf.open()
for f in ['01_源程序_前30页.pdf', '02_源程序_后30页.pdf']:
    d.insert_pdf(pymupdf.open(f))
d.save('上传用/源程序鉴别材料_前后各30页.pdf', garbage=4, deflate=True)
```

合并后**必核四项**：总页数 = 60；物理第 1 页页眉标「第 1 页」；
**物理第 31 页页眉须标「第 100 页」**（证明接的是真实后段位置）；末页标「第 129 页」。
再用 `re.findall(r'第\s*(\d+)\s*页', page.get_text())` 抽页眉页码逐页比对，别只看首页。

## 4. 交付物清单

```
软著申请材料/
├── 01_源程序_前30页.pdf      # 页眉含名称版本，页码 1–30
├── 02_源程序_后30页.pdf      # 页码接着真实位置（如 100–129）
├── 03_软件说明书.pdf         # 封面 + 目录 + 七章（概述/环境/部署/界面/操作/技术/声明）
├── 04_登记申请表_填写信息汇总.md   # 按 CPCC 字段组织，可直接复制进在线表单
├── 05_材料清单与办理指引.md        # 流程、官费、常见补正、风险提示、版本范围、备查说明
├── screenshots/              # 配图原图
└── 上传用/                   # 01+02 合并版 + 说明书副本，直接拖进系统上传框
```

**必做终检**（写成一个脚本，逐项打 ✅/❌）：
每个源程序 PDF 页数 = 30、页眉含「名称 版本」、页码连续、**每页正文 ≥ 50 行**；
说明书页眉一致、页码自 1 起连续、配图数、章节关键词齐全；三处名称版本一致；
封面各字段（含两个日期）齐全且 **dev ≤ pub**；
说明书全文**无 URL / 邮箱 / 手机号 / 第三方姓名**；
`04` 里身份证号、地址、邮编、电话、邮箱、发表链接**全部填实**（不放过任何「待填」）；
用 `pymupdf` 抽全文查占位符残留（`XXXX`/`待填`/`TODO`/`＿＿`）。

**材料生成后源码又改动，怎么办**（本项目实测踩到）：哪怕只加几十行，折行页数就会变
（129 页 → 131 页），`01`/`02` 的页码分配随之位移 ⇒ `04` 里的「源程序量 / 页数」与提交的 PDF 立刻脱节。
处理：**先如实测出新值**（`python junqi_srcdoc.py --probe` 只算不写），然后把两条路摆给用户选 ——
① **沿用旧 PDF**（源程序量按旧行数填，零成本）；② **重出**（新行数 + 新页数，且说明书截图也要重拍，
因为评分算法类改动会影响截图里的数值）。两条路都合规（登记的是版本快照），但**填的数字必须与提交的 PDF 对应**。

## 5. 四个高风险点，交付时必须主动说

1. **署名与权利人不一致** —— 代码/页面里的作者署名、公司名、合作者若与登记的著作权人不同，
   必须向用户点明：他人参与则不能按「独立开发」申报。这是最容易埋雷的地方。
   处理套路：把每个出现过的署名/网名/站点**列成一张表**，向用户逐条确认性质
   （本人网名 / 本人站点 / 他人 / 致敬语），确认后**写进 `04` 与说明书版权声明**
   （「著作权人网名：A、B、C；所用站点为本人所有；不存在合作开发者或第三方权利人」）——
   一句话就能挡掉审查员的疑问，比事后解释强得多。
2. **软件名称含他人商标** —— 建议去掉或不作为正式名称。
3. **发表状态与发表日期** —— 拿不出可验证的发表记录，就改报「未发表」，流程完全一样、证书效力相同；
   若按「已发表」申报，提醒用户**现在就把发表页截图存下来**（链接可能失效），
   且截图要同时含标题、日期、账号、URL。
4. **版本范围没定** —— 见 3b。多版本软件的源程序与截图必须同源。

## 6. 可复用脚本

`scripts/gen_source_pdf.py`（源程序 PDF）、`scripts/gen_manual_pdf.py`（说明书 PDF）、
`scripts/check_soft_docs.py`（全材料终检，含日期逻辑、网址/联系方式、第三方姓名、占位符拦截）。
使用时改顶部常量（源文件路径、输出目录、软件名称/版本/著作权人）。

项目侧配套（按软件类型改编，放在项目自己的 `.workbuddy/tests/` 下）：
配图采集脚本（headless Chrome 实拍各功能区）、**候选数据扫描脚本**（按黑名单筛示例数据，见 3c）、
内容丰富度探针（挑选步数/事件最全的样本）、**本人身份探针**（把候选数据的「己方/主体」逐份读出来，
筛出「主体 = 著作权人」且不敏感的，见 3d）、**逐图核验脚本**（重放每个截图状态，断言本人网名处处出现）。
